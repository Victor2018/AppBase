# AI 写代码很快，但它不知道你的目录结构：一个 Android 团队的 AI 编码落地记录

> 三个 Skill、两个 Command、两个 MCP，把 Figma、Swagger、TAPD 和团队规范接进对话。但真正决定成败的不是工具，而是项目本身有没有清晰的分层。

## 一、我们卡住的不是生成速度

让 AI 写一个登录页，它 30 秒能给你 200 行 Kotlin。问题是这 200 行大概率不能合并：

- 文件放错模块，包名是自己编的；
- 没有继承项目基类，响应封装绕过了统一解析；
- 控件 ID 用 `tvTitle`，而团队规范是 `tv_title`；
- 一个接口该写的 8~9 个文件，它只写了 3 个。

这不是模型能力问题。**AI 不缺口才，缺的是它不知道你的目录结构、命名规则和分层方式。** 它只见过公开代码，没见过你仓库里那套约定。

所以我们没有去调 prompt，而是先把「项目约定」变成 AI 能读、能执行、能自检的东西。这件事拆开看只有三步：把数据接进来、把规范写下来、把顺序固定下来。

## 二、先说前提：先有架构，再谈 AI

这是整篇文章里最想强调的一段。下面这套能力不是通用模板，它的每一条规则都是从项目现有代码里抄出来的。**在架构分层不明确的项目里，我建议先优化项目结构，而不是接 AI 工具。**

| 前提 | 说明 |
|---|---|
| 必须熟悉项目架构 | 先读 README、`settings.gradle`、模块职责、基础库、基类、响应封装与命名规范；能说清新代码该落在哪个模块 |
| 说明文档要能对上代码 | 架构说明、目录约定与代码不一致时先修文档；按错误文档写出的 Skill，产出只会错得更整齐 |
| 规则来自现有代码 | 基类名、包名、分层方式、响应封装、DI 方式，全部照搬工程现有实现，不另发明一套 |
| 按项目实际情况写 Skill | 别人项目的 Skill 只能当样例，换项目要重写 references，不能直接复制 |
| 分层不明确就不建议用 | 没有统一基类、网络封装和模块边界时，AI 只能猜；猜出来的代码进不了 Code Review |

怎么判断自己的项目适不适合，我们总结了一张表：

| 情况 | 建议 |
|---|---|
| 有基础库、统一响应封装、明确模块边界 | 可以直接试用 |
| 命名规范与目录约定有文档，且与代码一致 | 可以直接试用 |
| 规范只存在于个人经验，没有文档 | 先整理成文档，或先用 Skill 固化一版 |
| 分层不明确、同类代码有多种写法 | 先做架构收敛，再引入 AI |
| 想跳过项目认知直接生成 | 停下来；文件会放错模块、继承错基类 |

一个反直觉的结论：**同一套 Skill，在分层清晰的项目里省时间，在架构混乱的项目里放大混乱。** 因为 AI 会把你代码里已有的坏味道，按同样的效率批量复制。

## 三、三层能力：读得到、做得对、串得起来

我们把能力拆成三层，各管一件事，缺一层都跑不顺。

| 概念 | 作用 | 我们的例子 |
|---|---|---|
| MCP | 给 AI 提供工具和数据通道 | Figma MCP 读设计稿；TAPD MCP 读 Bug |
| Skill | 给出单点任务的流程、规范与检查清单 | 设计稿转 XML、接口链路分层、Bug 定位 |
| Command | 把多个 Skill 和 MCP 调用按固定顺序、固定门禁编排 | `/android-feature` 串起 UI → 接口 → 上屏 → 审查 |

- 只有 MCP：AI 能读到设计稿，但不知道该生成什么样的布局；
- 只有 Skill：AI 知道规范，但读不到 Figma 和 TAPD，还要人一步步触发；
- 只有 Command：能串起流程，但每个环节没有可依据的规范。

MCP 解决「读得到」，Skill 解决「做得对」，Command 解决「串得起来」。

## 四、三个 Skill：把规范写成可执行约束

Skill 是开放格式，一个目录 + 一份 `SKILL.md`（YAML frontmatter + Markdown 正文），需要细节时再挂 `references/`。没有插件，没有编译，纯文本。

我们写了三个，对应 Android 日常最机械、最易漏的三段：

| Skill | 输入 | 主要产出 |
|---|---|---|
| `figma-android-ui` | Figma / MasterGo / 即时设计 / 蓝湖 / Sketch / XD / PS 链接或截图 | XML 布局、Activity/Fragment 骨架、资源命名与 3x 切图清单 |
| `android-api-ds` | Swagger / Knife4j 文档链接或截图 | Req、Data、Api、ApiService、IDS、DS、VM、VMFactory、InjectorUtils |
| `fix-tapd-android-bug` | TAPD Bug 链接或 Bug ID | 根因分析、修复方案、最小范围的代码修改 |

第二个最能说明问题。一个接口在项目里要落地这些文件：

```
Req / Data / Api / ApiService / IDS / DS / VM / VMFactory / InjectorUtils
```

少了任何一层，编译能过，Review 过不了。人写久了会漏，AI 不知道要写——除非你把它写进 Skill 的检查清单。

`SKILL.md` 的 frontmatter 只有两个关键字段：

```markdown
---
name: android-api-ds
description: 根据 Swagger/Knife4j 文档生成 Retrofit 网络链路。
  当需要新增接口、补全 Req/Data/Api/DS/VM 时使用。
---
```

`description` 要写清「做什么 + 何时用」，多数客户端靠它自动匹配任务；正文写输入格式、执行步骤、约束和自检项；`references/` 放分层规则、命名规范、真实示例代码。

**这里最容易翻车的是「抄」。** 直接拿别人项目的 Skill，生成结果看起来对、结构却不对——包名、基类、响应封装全是别人的。返工成本比自己写还高。

## 五、Command：把顺序和门禁写死

单点 Skill 解决不了真实需求。一个功能往往是「新页面 + 新接口 + 数据上屏 + 提交审查」，需要连续调用多个 Skill，每次切换都要重新交代规范。

Command 就是一层编排，正文是普通 Markdown，写清阶段顺序、交接门禁和停止点。我们有两个：

| Command | 作用 | 是否改代码 |
|---|---|---|
| `/android-feature` | 四阶段串起 UI → 接口 → 上屏 → 审查 | 前三阶段改，第四阶段只审不改 |
| `/android-review` | 按项目规范审查改动，输出分级问题与最小修复方案 | 否 |

`/android-feature` 的四个阶段：

| 阶段 | 动作 | 产出 |
|---|---|---|
| 一、UI | 读 Figma 节点，生成 XML 与页面骨架，导出 3x 图 | 文件清单 + 自检结果 + 与设计稿的已知偏差 |
| 二、接口链路 | 生成 Req/Data/Api/ApiService/IDS/DS/VM/Factory，补 InjectorUtils | 文件清单 + 字段映射表 + 对文档未明确处的假设 |
| 三、数据上屏 | DS → VM → LiveData → UI，打通加载/有数据/空/失败四态 | 数据流说明 + 改动清单 |
| 四、审查 | 按 `/android-review` 标准审查全部改动 | 概览 + 问题表 + P0/P1/P2 修复建议 |

两个设计细节值得说：

1. **四阶段不可跳、不可乱序**，每阶段自检通过才能进下一步；默认在阶段间停下等人确认，`-y` 才连续跑到底。
2. **阶段四只审不改**。审查和修改分开，是为了让人在合入前真正看一遍，而不是让 AI 自己改完自己评。

## 六、Skill 不绑定客户端

这点对团队推广很关键：规范不该锁在某一个工具里。

Skill 是 Agent Skills 的开放约定，Command 是普通 Markdown，都不调用任何私有接口。Qoder、Cursor、Trae、CodeBuddy、Claude Code 都能读同一份内容。

换客户端时，要改的只有两处：

| 要素 | 是否通用 |
|---|---|
| `SKILL.md` 正文与 `references/` | 通用，不用改 |
| frontmatter 的 `name` / `description` | 通用，但要写准 |
| Skill 安装目录 | 不通用：项目级 `.xxx/skills/`，用户级 `~/.xxx/skills/` |
| 命令触发方式 | 不通用：斜杠命令、规则文件因工具而异 |
| MCP 配置位置 | 不通用：各客户端配置文件与开关不同 |

同一份 JSON 粘到不同入口，团队里用不同 IDE 的人可以共享同一套规范。这是我们把 Skill 而不是插件当载体做的主要原因。

## 七、怎么判断真的接好了

配置类问题最常见的表现是「看起来装了，其实没连上」。我们的验收标准只有两条：

- 状态点为绿色，且 **MCP 工具数不为 0**。我们的基线是 Figma 2 个工具、TAPD 18 个工具。
- 真正调用一次：执行 `tapd_list_workspaces`，或读一次 Figma 节点，能返回数据才算通。

工具数为 0、状态点变红，基本就是 `npx` 不可用、包下载失败或 token 无效，按顺序排查即可。

落地节奏我们按四段走，不追求一次性推广：

| 阶段 | 周期 | 做什么 |
|---|---|---|
| 准备期 | 1 天 | 配 MCP、装 Skill、读项目架构 |
| 试点期 | 1 周 | 各挑 1 个页面、1 个接口、1 个 Bug |
| 校准期 | 1 周 | 按试点结果改 references 与命令门禁 |
| 推广期 | 持续 | 提交前统一 review，每月复盘 |

## 八、几个踩过的坑

**1. 文档和代码不一致。** 按旧文档写的 Skill，产出的代码结构是「整洁的错误」。第一件事是让文档对上代码，而不是让 AI 猜。

**2. token 进了仓库或截图。** MCP 配置里带 Figma PAT 和 TAPD 令牌，真实文件只放本地并加进 `.gitignore`，仓库里只提交含 `<YOUR_TOKEN>` 的示例。分享截图前遮挡 token、workspace ID、Bug ID。一旦出现在聊天或提交记录里，立即撤销重发。

**3. 把 `-y` 当成质量控制。** `-y` 只跳过停顿，不跳过门禁。生成后必须编译、自测、Code Review——质量责任始终在人。

**4. 用生成结果代替判断。** Bug 修复场景尤其明显：Bug 描述经常不准，关键结论埋在评论里。Skill 里写死了「以评论中的技术结论为准」，否则 AI 会热情地修一个不存在的问题。

**5. 忘了「不覆盖」的边界。** 这套能力不管需求评审、服务端开发、自动化测试和发布上线。想让它全包，只会得到一份看起来很完整、实际没人负责的产出。

## 九、最后

回头看，这件事的价值不在「AI 帮我写了多少行」，而在于**同一类任务每次都能按同一标准完成**：页面按同一套命名，接口按同一套分层，Bug 按同一套证据链修复。

工具会换，模型会升级，但项目自己的目录结构、命名规则和分层方式不会因为换个客户端就消失——它们本来就该被写下来。

所以顺序别搞反：先把架构理清、把规范写下来，再让 AI 进来。**AI 不缺口才，缺的是它不知道你的目录结构、命名规则和分层方式。**
